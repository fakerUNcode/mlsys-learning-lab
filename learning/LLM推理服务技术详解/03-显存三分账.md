# 三、显存三分账

## 前置基础

**只用几个前置结论：**

1. **字节换算关系**：1 byte = 8 bit；$1\ \text{GB} = 10^9$ byte（十进制），$1\ \text{GiB} = 2^{30}$ byte（二进制）。fp16 占 **2 byte/元素**
2. **KV Cache 定义**（§1.4）：每层每个 token 需要缓存 **一份 K + 一份 V**，共 2 份
3. **HBM = High Bandwidth Memory，高带宽内存——就是显卡上那块"显存"本体**。你看到的 A100 80GB、H100 80GB，那个 80GB 指的就是它。
4. **trade-off = 取舍 / 权衡**。指一件事上**你没法两头都要**：往某个方向多拿一点，就必须在另一处等价地交出去一点。工程语境里它几乎总是同一个旋钮被往相反方向拉的结构。
5. **张量元素数 = 各维度尺寸连乘**

## 公式推导

### 推导一：模型权重显存

$$
\begin{aligned}
M_{\text{weight}} &= P \cdot b_{\text{param}} && \text{（总字节 = 参数个数 × 每参数字节）}\\
&= 7 \times 10^{9} \times 2 && \text{（代入：7B 参数，fp16 = 2 byte）}\\
&= 1.4 \times 10^{10}\ \text{byte} && \text{（乘法）}\\
&= 14.0\ \text{GB} && \text{（除以 }10^{9}\text{）}\\
&= 13.04\ \text{GiB} && \text{（除以 }2^{30}\text{）}
\end{aligned}
$$

> **工程提示**：口语说的"14 GB"是十进制；操作系统与 `nvidia-smi` 显示的通常是 GiB。同一块显存两种读法差 7.4%，调参时别被这个坑。

### 推导二：单 token 的 KV Cache 显存

先明确 $d_{\text{head}}$（每个注意力头的维度）从哪来：

$$
\begin{aligned}
d_{\text{head}} &= \frac{d_{\text{model}}}{n_q} && \text{（定义：模型总维度均分给 }n_q\text{ 个 Q 头）}\\
&= \frac{4096}{32} && \text{（代入 Llama-2 7B：}d_{\text{model}}{=}4096,\ n_q{=}32\text{）}\\
&= 128 && \text{（除法）}
\end{aligned}
$$

**注意**：$d_{\text{head}}$ 由 **Q 头数** $n_q$ 决定，而 KV 的份数由 **KV 头数** $n_{kv}$ 决定。这两者在 MHA （ Multi-Head Attention，多头注意力机制）下相等，在 GQA 下不等——这是后面压缩比的来源。

![img](https://fakercodes.oss-cn-hangzhou.aliyuncs.com/sl/20260914215525url_20260914215516_h1_acuf_ded875c18c4deca04c99bfe31ba037b1.png)

![img](https://fakercodes.oss-cn-hangzhou.aliyuncs.com/sl/20260914215528url_20260914215514_h1_rczf_b88f08194300712be5aae0bd9e81d578.png)
$$
\begin{aligned}
每token 占用的 KV Cache显存 S_{kv} &= 2 \cdot L \cdot n_{kv} \cdot d_{\text{head}} \cdot b_{kv} && \text{（K 与 V 各 1 份 × 层数 × KV 头数 × 头维度 × 每元素字节）}\\
&= 2 \times 32 \times 32 \times 128 \times 2 && \text{（代入 Llama-2 7B MHA 配置）}\\
&= 524288\ \text{byte} && \text{（连乘）}\\
&= 0.500\ \text{MiB} && \text{（除以 }2^{20}\text{）}
\end{aligned}
$$

### 推导三：GQA 的压缩比

- **MHA（Multi-Head Attention，多头注意力）**：每个 Q 头有**一一对应**的 K 头和 V 头。
- **GQA（Grouped-Query Attention，分组查询注意力）**：**几个 Q 头分成一组，共享一组 K/V**。

- **MQA（Multi-Query Attention，多查询注意力）** ：**Key 和 Value 只保留一份**，由所有头共享



```
                32 个 Q Heads
                      │
      ┌───────────────┼───────────────┐
      ↓               ↓               ↓

MHA       32 KV Heads     每 1 个 Q 共享 1 KV
          ████████████████████████████████

GQA        8 KV Heads     每 4 个 Q 共享 1 KV
          ████████

MQA        1 KV Head      32 个 Q 共享 1 KV
          █
```


$$
\begin{aligned}
\rho &= \frac{S_{kv}^{\text{MHA}}}{S_{kv}^{\text{GQA}}} && \text{（压缩比定义：优化前 ÷ 优化后）}\\
&= \frac{2 L n_{kv}^{\text{MHA}} d_h b}{2 L n_{kv}^{\text{GQA}} d_h b} && \text{（代入推导二的公式）}\\
&= \frac{n_{kv}^{\text{MHA}}}{n_{kv}^{\text{GQA}}} && \text{（分子分母约去公因子 }2 L d_h b\text{）}\\
&= \frac{32}{8} && \text{（代入 Llama-3 8B：32 → 8）}\\
&= 4 && \text{（除法）}
\end{aligned}
$$

**这就是"新模型普遍上 GQA"的全部数学**：KV 头数除以 4，KV Cache 直接除以 4，同样显存下**并发能力翻 4 倍**。而 $d_{\text{head}}$ 不变（仍由 $n_q = 32$ 决定），模型容量基本不受影响。

MQA 似乎 KV更少，为什么我们还是倾向于 GQA？

**GQA 在“推理效率”和“模型质量”之间取得了比 MQA 更好的平衡。**

如果只追求 KV Cache 最小，当然 MQA 更狠：

\[ \text{MHA} \rightarrow \text{GQA} \rightarrow \text{MQA} \]

对应 KV Head：

\[ 32\rightarrow8\rightarrow1 \]

但 KV Head 越少，意味着**越来越多 Q Head 被迫共享同一套 K/V 表征**。这会逐渐成为模型表达能力的瓶颈。

#### 为什么 32 → 8 往往很划算？

看 KV Cache 公式：

\[ S_{KV} = 2L n_{kv} d_{\text{head}}b \]

显存和 \(n_{kv}\) 成正比。

假设其他条件完全相同：

| 架构    | Q Head | KV Head | 相对 KV Cache | KV 表征数量 |
| ------- | ------ | ------- | ------------- | ----------- |
| MHA     | 32     | 32      | 100%          | 32          |
| **GQA** | 32     | **8**   | **25%**       | **8**       |
| MQA     | 32     | 1       | 3.125%        | 1           |

从 MHA → GQA：

\[ 32\rightarrow8 \]

已经得到：

\[ \boxed{4\times\text{ KV Cache 压缩}} \]

也就是减少：

\[ 75\% \]

但仍然保留 **8 组独立 KV**。

继续从 GQA → MQA：

\[ 8\rightarrow1 \]

确实还能继续降低 KV Cache，但此时开始走向“所有 Q Head 共用一套 KV”的极端，模型质量/容量方面的 trade-off 更激进。

所以工程上 GQA 往往处于一个很舒服的位置：

\[ \boxed{ \text{大部分 MQA 的推理收益} + \text{更接近 MHA 的模型质量} } \]

#### 对 LLM Serving 还有一个重要优势

Decode 阶段经常受到 **Memory Bandwidth** 限制。

每生成一个新 token，都需要读取大量历史：

\[ K_{\text{cache}},V_{\text{cache}} \]

如果 KV Cache 很大：

```
HBM
 │
 │ 大量读取 KV Cache
 ↓
GPU SM
 │
 ↓
Attention
```

内存带宽压力很大。

GQA 把 KV Cache 从：

\[ 32\text{ heads} \rightarrow 8\text{ heads} \]

那么不仅是“显存容量减少”，还意味着 Attention Decode 时**需要从 HBM 搬运的 KV 数据也显著减少**。

因此通常同时改善：

\[ \boxed{\text{KV Cache容量}} \]

和

\[ \boxed{\text{KV Cache内存带宽}} \]

最终有利于更高的并发、batch size 和推理吞吐。

### 推导四：显存守恒 → 最大并发数

$$
\begin{aligned}
M_{\text{kv}} &= M_{\text{total}} - M_{\text{weight}} - M_{\text{act}} - M_{\text{resv}} && \text{（显存守恒：总量减去固定占用）}\\
&= 80 - 14 - 4 && \text{（代入 A100 80GB：权重 14，激活+预留 4，单位 GB）}\\
&= 62\ \text{GB} && \text{（减法）}
\end{aligned}
$$

单条请求占用（序列长度 $s = 1000$）：

$$
\begin{aligned}
M_{\text{req}} &= S_{kv} \cdot s && \text{（线性增长：每 token 一份，共 }s\text{ 份）}\\
&= 524288 \times 1000 && \text{（代入）}\\
&= 5.24 \times 10^{8}\ \text{byte} && \text{（乘法）}\\
&\approx 524\ \text{MB} && \text{（除以 }10^{9}\text{）}
\end{aligned}
$$

$$
\begin{aligned}
最大并发数N_{\text{conc}} &= \frac{M_{\text{kv}}}{M_{\text{req}}} && \text{（并发数 = 可用显存 ÷ 单条占用）}\\
&= \frac{62 \times 10^{9}}{5.24 \times 10^{8}} && \text{（代入，统一为 byte）}\\
&\approx 118 && \text{（除法取整）}
\end{aligned}
$$

换成 GQA 后 $M_{\text{req}} \approx 131\ \text{MB}$：

$$
\begin{aligned}
N_{\text{conc}}^{\text{GQA}} &= \frac{62 \times 10^{9}}{1.31 \times 10^{8}} && \text{（代入 GQA 的单条占用）}\\
&\approx 473 && \text{（除法取整）}
\end{aligned}
$$

**118 → 473，正好 4 倍**，与推导三的压缩比 $\rho = 4$ 完全吻合（互相验证）。

### 推导五：PagedAttention 的碎片账

**旧方案（按最大长度预分配）**：给请求预留 $L_{\max}$ 的连续显存，实际只用 $L_{\text{act}}$。

$$
\begin{aligned}
w_{\text{pre}} &= 1 - \frac{L_{\text{act}}}{L_{\max}} && \text{（浪费率 = 1 − 利用率）}\\
&= 1 - \frac{1500}{4096} && \text{（代入：实际 1500，预留 4096）}\\
&\approx 0.63 && \text{（计算）}
\end{aligned}
$$

实测常见 60%~80%。

**新方案（PagedAttention 分页）**：把 KV Cache 切成数个==含有固定 $B_k$ 个 token== 的**块（Block）**，用多少分多少。**逻辑上连续，物理上可以散着放**。只有最后一块没填满，平均浪费半块：

<img src="https://fakercodes.oss-cn-hangzhou.aliyuncs.com/sl/image-20260914222445052.png" alt="image-20260914222445052" style="zoom: 25%;" />
$$
\begin{aligned}
w_{\text{page}} &= \frac{B_k / 2}{L_{\text{act}}} && \text{（最后一块平均半空 ÷ 实际总长度）}\\
&= \frac{16 / 2}{1000} && \text{（代入：块大小 16，实际长度 1000）}\\
&= 0.008 && \text{（除法）}
\end{aligned}
$$

**浪费率从 63% 降到 0.8%**。加上消除外部碎片，实测从 60%+ 降到 4% 以下。

**额外红利**：不同请求若共享相同前缀（如同一份 System Prompt），那些**块可以共享**（写时复制 Copy-on-Write），这是 Prefix Cache 的天然实现。

## 程序实例

```python
GB, GiB, MiB = 1e9, 2**30, 2**20

def kv_per_token(n_layers, n_kv_heads, head_dim, dtype_bytes=2):
    """单 token KV Cache 字节数：K、V 各一份。"""
    return 2 * n_layers * n_kv_heads * head_dim * dtype_bytes

def capacity(total_GB, params, dtype_bytes, act_resv_GB, seq_len, **kv_cfg):
    """给定硬件与模型配置，返回可容纳的并发请求数。"""
    weight = params * dtype_bytes
    avail  = total_GB * GB - weight - act_resv_GB * GB
    per_req = kv_per_token(dtype_bytes=dtype_bytes, **kv_cfg) * seq_len
    return weight / GB, avail / GB, avail / per_req

# Llama-2 7B (MHA: 32 KV heads) vs Llama-3 8B (GQA: 8 KV heads)
for name, nkv in (("MHA 32头", 32), ("GQA  8头", 8)):
    w, avail, n = capacity(
        total_GB=80, params=7e9, dtype_bytes=2, act_resv_GB=4,
        seq_len=1000, n_layers=32, n_kv_heads=nkv, head_dim=128)
    print(f"{name}: 权重={w:.1f}GB  KV可用={avail:.1f}GB  并发={n:.0f}条")

print("\n单 token KV:  MHA=%.3f MiB   GQA=%.3f MiB"
      % (kv_per_token(32, 32, 128) / MiB, kv_per_token(32, 8, 128) / MiB))
```

**实际运行输出**：

```
MHA 32头: 权重=14.0GB  KV可用=62.0GB  并发=118条
GQA  8头: 权重=14.0GB  KV可用=62.0GB  并发=473条

单 token KV:  MHA=0.500 MiB   GQA=0.125 MiB
```

## 部署说明

**KV Cache 不是越大越好，而是"留给 KV 的显存越大，并发越高"**。四个可调旋钮：

| 旋钮 | 怎么做 | 代价 |
|---|---|---|
| **降精度** | KV Cache 用 FP8 / INT8 | 轻微精度损失 |
| **换模型** | 优先选 GQA / MQA 架构 | — |
| **分页管理** | 用 vLLM / SGLang 的 PagedAttention | 几乎无代价，纯赚 |
| **限制长度** | 设 `max_model_len` 上限 | 超长请求被拒 |

**vLLM 典型配置**：

```bash
python -m vllm.entrypoints.openai.api_server \
    --model meta-llama/Llama-2-7b-hf \
    --max-model-len 4096 \            # 限制单请求最大长度，防止一条请求吃光 KV
    --gpu-memory-utilization 0.90 \   # 显存水位；留 10% 给激活峰值，防 OOM
    --max-num-seqs 256 \              # 最大并发序列数（准入控制硬闸门）
    --kv-cache-dtype fp8_e5m2 \       # KV 量化，并发近乎翻倍
    --enable-prefix-caching           # 开启前缀共享，复用共享块的 KV
```

**`--gpu-memory-utilization` 为什么不能设 0.99**：激活值工作区会随 batch 峰值波动（§四还会看到平方级的注意力矩阵），留 8%~12% 余量是防止 OOM 触发抢占的经验值。

## 直观理解

> 显存像一间面积固定的仓库。货架（权重）摆进去就占死；每位客人的暂存箱（KV Cache）随聊天变长越堆越多；过道（激活值）只在搬运时临时占。仓库剩下的面积，决定能同时接待几位客人——而旧办法给每位客人预留一整排空货架（碎片），新办法按箱计费（分页）。
