# 五、带宽与算力

**这一章是全文的枢纽**：它解释了"为什么 Prefill 和 Decode 必须分开调度"，也解释了"为什么量化能直接提速"。

## 前置基础

**只用三个前置结论：**

1. **一次乘加 = 2 FLOPs**：计算 $y = wx + b$ 含 1 次乘法 + 1 次加法，记为 2 次浮点运算
2. **参数量 ↔ FLOPs 换算**：把 $P$ 个参数全部用一遍，需要 $2P$ FLOPs
3. **时间 = 工作量 ÷ 速率**（匀速模型）：$\text{时间} = \dfrac{\text{字节数}}{\text{带宽}}$，或 $\dfrac{\text{FLOPs}}{\text{算力}}$

**新增概念——算术强度（Arithmetic Intensity）**：

$$
\begin{aligned}
I &= \frac{\text{FLOPs}}{\text{Bytes}} && \text{（定义：每搬运 1 字节所伴随的计算量）}
\end{aligned}
$$

它衡量"**数据搬来一趟，被反复用了多少次**"。$I$ 越大，越能摊薄搬运成本。

## 公式推导

### 推导一：机器的平衡点

GPU 有两个理论峰值：算力峰值 $\mathcal{F}$（FLOP/s）与带宽峰值 $\mathcal{B}$（byte/s）。

$$
\begin{aligned}
t_{\text{calc}} &= \frac{\text{FLOPs}}{\mathcal{F}} && \text{（时间 = 工作量 ÷ 速率，用于计算）}\\
t_{\text{mem}} &= \frac{\text{Bytes}}{\mathcal{B}} && \text{（时间 = 工作量 ÷ 速率，用于搬运）}\\
t_{\text{step}} &= \max(t_{\text{calc}},\ t_{\text{mem}}) && \text{（两者重叠执行，实际取较慢者）}
\end{aligned}
$$

两者相等时的算术强度就是**机器平衡点** $I^{*}$：

$$
\begin{aligned}
\frac{\text{FLOPs}}{\mathcal{F}} &= \frac{\text{Bytes}}{\mathcal{B}} && \text{（令两时间相等）}\\
\frac{\text{FLOPs}}{\text{Bytes}} &= \frac{\mathcal{F}}{\mathcal{B}} && \text{（移项：左移 Bytes，右移 }\mathcal{B}\text{）}\\
I^{*} &= \frac{\mathcal{F}}{\mathcal{B}} && \text{（左边即 }I\text{ 的定义）}
\end{aligned}
$$

代入 A100（fp16 稠密算力 312 TFLOP/s，HBM 带宽 2.0 TB/s）：

$$
\begin{aligned}
I^{*} &= \frac{312 \times 10^{12}}{2.0 \times 10^{12}} && \text{（代入，统一为 FLOP/s 与 byte/s）}\\
&= 156\ \text{FLOP/byte} && \text{（除法）}
\end{aligned}
$$

**判据**：
- 若 $I < I^{*}$ → **Memory-bound（带宽瓶颈）**，算力在空转
- 若 $I > I^{*}$ → **Compute-bound（算力瓶颈）**

### 推导二：Decode 的算术强度

Decode 一步：batch 为 $B$，每个请求只用 1 个 token。

$$
\begin{aligned}
\text{FLOPs}_{\text{dec}} &= 2 P \cdot B && \text{（每请求每步过一遍全模型 }2P\text{ FLOPs，共 }B\text{ 个请求）}\\
\text{Bytes}_{\text{dec}} &= 2 P + B \cdot S_{kv} \cdot s && \text{（读一遍 fp16 权重 }2P\text{，加上读 }B\text{ 份 KV Cache）}\\
I_{\text{dec}} &= \frac{2 P B}{2 P + B S_{kv} s} && \text{（代入 }I\text{ 的定义）}\\
&\approx \frac{2 P B}{2 P} && \text{（当 }B S_{kv} s \ll 2P\text{，即 KV 相对权重可忽略时）}\\
&= B && \text{（约去 }2P\text{）}
\end{aligned}
$$

**$I_{\text{dec}} \approx B$（批大小）**。要让 decode 达到 156 的平衡点，需要 $B \approx 156$——但 §三算出显存只允许并发 118 条（MHA 配置），**所以 decode 几乎永远处在带宽瓶颈区**。

**这正是"Decode 是 Memory-bound"的完整证明**，也解释了为什么 decode 必须拼命堆 batch。

### 推导三：Prefill 的算术强度

Prefill 一次处理 $s$ 个 token，**权重只需从 HBM 读一次**（被所有 token 复用）：

$$
\begin{aligned}
\text{FLOPs}_{\text{pre}} &= 2 P \cdot s && \text{（每 token 过一遍全模型，共 }s\text{ 个 token）}\\
\text{Bytes}_{\text{pre}} &= 2 P && \text{（权重只读一遍；激活读写相对小，此处忽略）}\\
I_{\text{pre}} &= \frac{2 P s}{2 P} && \text{（代入定义）}\\
&= s && \text{（约去 }2P\text{）}
\end{aligned}
$$

**$I_{\text{pre}} \approx s$（序列长度）**。

**交叉点**：

$$
\begin{aligned}
I_{\text{pre}} &= I^{*} && \text{（令两者相等求临界长度）}\\
s &= 156 && \text{（代入 }I^{*}{=}156\text{）}
\end{aligned}
$$

**结论**：Prompt 长度超过约 156 token，Prefill 就进入算力瓶颈区。而真实场景的 Prompt 动辄几百到几万 token——**所以 Prefill 几乎永远是 Compute-bound**。

**这就是 Prefill 与 Decode 的对照表为什么长那样**：

| | Prefill | Decode |
|---|---|---|
| 算术强度 | $I \approx s$（几百~几万） | $I \approx B$（几十~上百） |
| 与 $I^{*}{=}156$ 比较 | **远大于 → 算力瓶颈** | **远小于 → 带宽瓶颈** |
| 优化杠杆 | 堆算力、TP 并行 | 堆 batch、量化减字节 |

### 推导四：TPOT 的物理下限

Decode 每一步**必须**把全部权重从 HBM 读一遍，这是绕不开的：

$$
\begin{aligned}
\tau_{\min} &= \frac{\text{Bytes}_{\text{dec}}}{\mathcal{B}} && \text{（时间 = 字节数 ÷ 带宽，Memory-bound 下取此项）}\\
&= \frac{2P}{\mathcal{B}} && \text{（忽略 KV 项，取理论下限）}\\
&= \frac{14 \times 10^{9}}{2.0 \times 10^{12}} && \text{（代入 7B fp16 权重 14 GB）}\\
&= 7.0 \times 10^{-3}\ \text{s} && \text{（除法）}\\
&= 7.0\ \text{ms} && \text{（换算为毫秒）}
\end{aligned}
$$

**7B fp16 模型在 A100 上的 TPOT 理论下限就是 7 ms**——再怎么优化调度也下不去，因为**光是把权重搬一遍就要 7 ms**。

若权重**量化到 INT8**（7 GB）：

$$
\begin{aligned}
\tau_{\min}^{\text{int8}} &= \frac{7 \times 10^{9}}{2.0 \times 10^{12}} && \text{（代入量化后的字节数）}\\
&= 3.5\ \text{ms} && \text{（除法并换算）}
\end{aligned}
$$

**量化让 TPOT 下限直接减半。** 这就是"量化不只是省显存，更是直接提升 decode 速度"的定量证明。

## 程序实例

```python
# A100-80GB SXM 参考值
FLOPS_PEAK = 312e12   # fp16 稠密算力 FLOP/s
BW_PEAK    = 2.0e12   # HBM 带宽 byte/s
P_7B       = 7e9

def report(P, dtype_bytes=2):
    I_star = FLOPS_PEAK / BW_PEAK
    weight = P * dtype_bytes
    tau_min = weight / BW_PEAK
    pre_T = FLOPS_PEAK / (2 * P)          # prefill 吞吐
    print(f"机器平衡点 I*      = {I_star:.0f} FLOP/byte")
    print(f"权重 fp{dtype_bytes*8}           = {weight/1e9:.1f} GB")
    print(f"TPOT 理论下限      = {tau_min*1e3:.2f} ms")
    print(f"Prefill 理论吞吐   = {pre_T/1e3:.1f}k token/s")
    print(f"Prefill 转算力瓶颈的临界长度 s = {I_star:.0f} token\n")

print("--- Llama-2 7B fp16 ---");  report(P_7B, 2)
print("--- Llama-2 7B int8 ---");  report(P_7B, 1)
```

**实际运行输出**：

```
--- Llama-2 7B fp16 ---
机器平衡点 I*      = 156 FLOP/byte
权重 fp16          = 14.0 GB
TPOT 理论下限      = 7.00 ms
Prefill 理论吞吐   = 22.3k token/s
Prefill 转算力瓶颈的临界长度 s = 156 token

--- Llama-2 7B int8 ---
机器平衡点 I*      = 156 FLOP/byte
权重 fp8           = 7.0 GB
TPOT 理论下限      = 3.50 ms
Prefill 理论吞吐   = 22.3k token/s
Prefill 转算力瓶颈的临界长度 s = 156 token
```

## 部署说明

**按本章结论，部署时的决策树**：

1. **先测你自己在哪种瓶颈区**
   - 提高 batch，吞吐显著上升 → 还在带宽瓶颈区，**继续加 batch**
   - 提高 batch，吞吐几乎不动、延迟线性上升 → 已进入算力瓶颈区，**停止加 batch**
2. **Decode 侧的提速优先级**：权重量化 > 增大 batch > 算子融合（CUDA Graph 减少 kernel launch 开销）
3. **Prefill 侧的提速优先级**：Prefix Cache 命中 > TP 并行（切分矩阵降低单步延迟）> 更高算力卡
4. **两者冲突时**：如果 TTFT 与 TPOT 的 SLO 都很严，考虑 **PD 分离**（§六）

## 直观理解

> Prefill 像用复印机复印整本手册：机器高速运转，时间花在"印"上。Decode 像每写一个字都要把整本手册从库房搬来翻一遍：时间全花在"搬"上。想省搬运，最有效的办法是叫上一群人一起写——一次搬运服务所有人（增大 batch），或者把手册印薄一点（量化）。
