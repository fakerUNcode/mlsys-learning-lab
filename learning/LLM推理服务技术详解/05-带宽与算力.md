

这一章要解决一个非常核心的问题：

> **大模型推理到底是在等 GPU 计算，还是在等数据搬运？**

理解这个问题以后，很多推理优化技术就不再需要死记：

- 为什么 Prefill 和 Decode 性能特征不同？
- 为什么 Decode 喜欢增大 Batch？
- 为什么量化不仅省显存，还可能提高生成速度？
- 为什么 Prefill 更关注 GPU 算力？
- 为什么推理系统会考虑 Prefill-Decode 分离？

这些问题背后实际上都指向两个词：

**Compute（计算）\**和\**Memory Bandwidth（显存带宽）**。

------

# 1. 先看本质

GPU 执行一次神经网络计算，大体要做两件事情：

```text
        HBM / 显存
            │
            │ ① 搬数据
            ▼
      ┌───────────┐
      │ GPU计算单元 │
      │ Tensor Core│
      │ CUDA Core │
      └───────────┘
            │
            │ ② 做计算
            ▼
          结果
```

例如计算：

$y=wx$

GPU 至少需要：

```text
显存
 │
 ├──读取 w
 ├──读取 x
 │
 ▼
GPU
 │
 └──执行 w × x
```

所以程序慢下来通常有两种原因。

### 情况 A：搬得太慢

GPU：

> 数据呢？我已经算完了。

计算单元大量等待显存。

这叫：

**Memory-bound（带宽受限）**

------

### 情况 B：算得太慢

显存：

> 数据早就送过去了，你还没算完。

这叫：

**Compute-bound（算力受限）**

------

因此判断一个 GPU 工作负载性能的第一步不是问：

> GPU 有多少 TFLOPS？

而应该问：

> **当前任务究竟是在等数据，还是在等计算？**

------

# 2. 前置基础

本章只需要三个旧知识。

## 2.1 FLOP

FLOP 可以理解为一次浮点运算。

例如：

$y=wx+b$

包含：

$w\times x$

一次乘法，以及

$(wx)+b$

一次加法。

因此：

$1\text{ multiply} + 1\text{ add} = 2\text{ FLOPs}$

所以一次乘加通常记作：

$2\text{ FLOPs}$

------

## 2.2 参数量与计算量

假设模型有：

$P$

个参数。

如果每个参数参与一次乘加，那么一个 token 完整经过模型时，可以粗略认为需要：

$2P\text{ FLOPs}$

例如 7B 模型：

$P=7\times10^9$

那么单 token 的粗略计算量：

$2P$$= 14\times10^9 \text{ FLOPs}$

也就是约：

$14\text{ GFLOPs}$

注意：

这里是为了建立性能模型而使用的近似，并不是在精确统计 Transformer 每一个算子。

------

## 2.3 时间公式

我们会反复使用一个非常简单的关系：

$\text{时间} = \frac{\text{工作量}} {\text{工作速度}}$

如果讨论计算：

$t_{\text{calc}} = \frac{\text{FLOPs}} {\mathcal F}$

如果讨论显存搬运：

$t_{\text{mem}} = \frac{\text{Bytes}} {\mathcal B}$

### 符号说明

- $t_{\text{calc}}$：计算所需时间
- $t_{\text{mem}}$：显存搬运所需时间
- $\mathcal F$：GPU 计算速度，单位 FLOP/s
- $\mathcal B$：显存带宽，单位 byte/s

例如：

```text
要搬 14 GB
显存每秒能搬 2 TB

时间 ≈ 14 GB ÷ 2 TB/s
```

这就是后面推导 Decode TPOT 下限的核心思想。

------

# 3. 算术强度

现在需要引入本章最重要的量：

**Arithmetic Intensity，算术强度。**

定义：

$I = \frac{\text{FLOPs}} {\text{Bytes}}$

### 符号说明

- $I$：算术强度
- FLOPs：完成任务需要的浮点运算次数
- Bytes：完成任务需要从内存层次搬运的数据量

单位：

$\text{FLOP/byte}$

它回答的问题非常直观：

> **每从显存搬 1 Byte 数据回来，我能拿它做多少计算？**

------

## 3.1 一个极端例子

假设搬回来 1 GB 数据。

程序 A：

```text
搬 1 GB
↓
只算一下
↓
结束
```

程序 B：

```text
搬 1 GB
↓
反复计算很多次
↓
结束
```

那么：

$I_A$更小，即程序 A 的算数强度更小

程序 A 更容易受**带宽**限制。

程序 B 更容易受**算力**限制。

因此可以粗略记忆：

```text
I 小
│
├─ 数据搬很多
├─ 数据复用少
└─ 容易 Memory-bound


I 大
│
├─ 数据复用多
├─ 每份数据做很多计算
└─ 容易 Compute-bound
```

所以算术强度本质上是在衡量：

> **搬一次数据回来，究竟榨出了多少计算价值。**

------

# 4. 机器平衡点

现在出现一个关键问题：

> $I$ 到底多大才算“大”？

不能凭感觉判断。

因为不同 GPU 的算力和带宽比例不同。

所以需要定义一个 GPU 自己的临界点：

$I^*$

称为：

**机器平衡点（Machine Balance Point）**

------

## 4.1 两种耗时

对于一个任务：

计算时间：

$t_{\text{calc}} = \frac{\text{FLOPs}} {\mathcal F}$

显存时间：

$t_{\text{mem}} = \frac{\text{Bytes}} {\mathcal B}$

在简化 Roofline 模型下，计算和内存传输可以有一定重叠，因此整体性能最终受较慢的一方限制：

$t_{\text{step}} \approx \max \left( t_{\text{calc}}, t_{\text{mem}} \right)$

### 符号说明

- $t_{\text{step}}$：当前步骤总耗时
- $\max(\cdot)$：取两者中较大的值

如果：

$t_{\text{mem}} > t_{\text{calc}}$

说明：

```text
计算早结束
   ↓
等待数据
   ↓
Memory-bound
```

反之：

$t_{\text{calc}} > t_{\text{mem}}$

说明：

```text
数据已经准备好
   ↓
计算还没完成
   ↓
Compute-bound
```

------

# 5. 推导平衡点

临界状态就是：

$t_{\text{calc}} = t_{\text{mem}}$

代入前面的定义：

$\frac{\text{FLOPs}} {\mathcal F} = \frac{\text{Bytes}} {\mathcal B}$

将 $\mathcal F$ 与 Bytes 移到对应一侧：

$\frac{\text{FLOPs}} {\text{Bytes}} = \frac{\mathcal F} {\mathcal B}$

左边正是算术强度：

$I = \frac{\text{FLOPs}} {\text{Bytes}}$

因此得到：

$\boxed{ I^* = \frac{\mathcal F} {\mathcal B} }$

这就是机器平衡点。

------

# 6. A100 示例

沿用原笔记中的简化参考值：

$\mathcal F = 312\times10^{12} \text{ FLOP/s}$$\mathcal B = 2.0\times10^{12} \text{ byte/s}$

所以：

$I^* = \frac{ 312\times10^{12} }{ 2.0\times10^{12} }$

约去：

$10^{12}$

得到：

$\boxed{ I^* = 156\text{ FLOP/byte} }$

这意味着：

> 对这个简化模型来说，每搬运 1 Byte 数据，如果平均能支撑约 156 FLOPs，计算能力和显存带宽才大致达到平衡。

于是得到本章最重要的判据：

$I\Rightarrow \text{Memory-bound}$

而：

$I>I^*$$\Rightarrow \text{Compute-bound}$

可以画成：

```text
性能瓶颈

Memory-bound                  Compute-bound
     │                              │
     │                              │
─────┼────────────────●─────────────┼────→ I
                    I*=156

      数据搬运限制             计算限制
```

------

# 7. 为什么 Decode 特殊

现在进入 LLM 推理。

Decode 的特点是：

> **每一次只生成一个新 token。**

例如：

```text
已有：
今天天气很

Decode #1：
今天天气很好

Decode #2：
今天天气很好，

Decode #3：
今天天气很好，适

Decode #4：
今天天气很好，适合
```

每一步只增加一个 token。

问题在于：

> 虽然只生成一个 token，但这个 token 仍然需要经过整个模型。

所以会出现一个非常不划算的现象：

```text
生成 1 token
      │
      ▼
读取整个模型的大量权重
      │
      ▼
做一次前向计算
      │
      ▼
得到 1 token
```

这正是 Decode 容易 Memory-bound 的根源。

------

# 8. Decode 强度

设：

- 模型参数量为 $P$
- Batch Size 为 $B$
- 单 token KV Cache 大小为 $S_{kv}$
- 当前上下文长度为 $s$

一次 Decode Step 中，粗略计算量：

$\text{FLOPs}_{dec} = 2PB$

### 为什么？

一个请求：

$2P$

个 FLOPs。

现在同时处理 $B$ 个请求：

$2P\times B$

所以：

$\text{FLOPs}_{decode} = 2PB$

------

## 8.1 搬多少数据？

如果使用 FP16 权重，每个参数：

$2\text{ Bytes}$

所以权重大小：

$2P\text{ Bytes}$

同时 Decode 还需要读取 KV Cache。

因此：

$\text{Bytes}_{decode} = 2P + BS_{kv}s$

于是：

$I_{dec} = \frac{ 2PB }{ 2P+BS_{kv}s }$

### 符号说明

- $I_{dec}$：Decode 算术强度
- $B$：Batch Size
- $S_{kv}$：单 token 的 KV Cache 字节量
- $s$：上下文长度
- $P$：模型参数量

------

# 9. 为什么约等于 B

如果当前场景中：

$BS_{kv}s \ll 2P$

也就是：

> KV Cache 搬运量相对于模型权重搬运量还比较小。

那么分母：

$2P+BS_{kv}s$

可以近似看成：

$2P$

于是：

$I_{dec} \approx \frac{2PB}{2P}$

约掉 $2P$：

$\boxed{ I_{dec} \approx B }$

这个结论非常重要。

它意味着：

> **Decode 的算术强度，很大程度上由 Batch Size 决定。**

------

# 10. Batch 为什么提速

假设：

$B=1$

那么粗略：

$I_{dec}\approx1$

而 A100 的平衡点是：

$I^*=156$

两者差距巨大：

$1\ll156$

所以 GPU 很可能处于：

**Memory-bound**

------

如果：

$B=32$

那么：

$I_{dec}\approx32$

虽然还是：

$32<156$

但已经比 $B=1$ 好很多。

为什么？

因为权重从 HBM 搬过来一次以后，可以同时服务更多请求：

```text
               一份模型权重
                    │
          ┌─────────┼─────────┐
          ▼         ▼         ▼
       请求 1     请求 2    ... 请求 B
          │         │         │
          └─────────┼─────────┘
                    ▼
              更多计算工作
```

因此增大 Batch 本质上是在：

> **提高同一份权重的复用率。**

这也是 Continuous Batching 对 LLM Serving 如此重要的硬件原因之一。

------

# 11. 一个重要修正

不要把：

$I_{dec}\approx B$

理解成永远成立。

它有一个明确前提：

$BS_{kv}s \ll 2P$

当上下文越来越长、Batch 越来越大时，KV Cache 流量可能不能再忽略。

这时应该回到完整公式：

$I_{dec} = \frac{ 2PB }{ 2P+BS_{kv}s }$

也就是说：

> **长上下文 Decode 不仅会受模型权重带宽影响，也会越来越受到 KV Cache 带宽影响。**

所以“Decode 是 Memory-bound”这个结论仍然成立，但瓶颈中的数据来源可能从“主要搬权重”逐渐变成“权重 + KV Cache”。

------

# 12. Prefill 为什么不同

Prefill 是：

> 一次处理 Prompt 中的一批 token。

例如输入：

```text
请解释一下为什么 Transformer 需要 KV Cache
```

假设共有 $s$ 个 token。

Prefill 可以把这些 token 组织成较大的矩阵运算。

于是权重具有很高的复用率。

直观来看：

```text
                    模型权重
                       │
                       ▼
         ┌───────────────────────┐
         │                       │
token 1 ─┤                       │
token 2 ─┤      大型矩阵计算      │
token 3 ─┤                       │
  ...    │                       │
token s ─┤                       │
         └───────────────────────┘
```

同一批权重服务很多 token。

这和 Decode：

```text
一个 token ← 大量模型权重
```

形成鲜明对比。

------

# 13. Prefill 强度

沿用原笔记中的简化模型。

$s$ 个 token，每个 token 大约：

$2P$

FLOPs。

所以：

$\text{FLOPs}_{pre} = 2Ps$

假设这一批 token 计算过程中，模型权重主要从 HBM 搬一次：

$\text{Bytes}_{pre} \approx 2P$

于是：

$I_{pre} = \frac{2Ps}{2P}$

约掉 $2P$：

$\boxed{ I_{pre} \approx s }$

这意味着：

> **序列越长，权重被复用得越充分，算术强度越高。**

------

# 14. Prefill 临界点

A100 简化平衡点：

$I^*=156$

而：

$I_{pre}\approx s$

令两者相等：

$I_{pre}=I^*$

代入：

$s=156$

因此在这个高度简化的模型里：

$s>156$

时就开始进入 Compute-bound 一侧。

真实 Prompt 很容易达到数百甚至数千 token，因此 Prefill 往往具有远高于单请求 Decode 的算术强度。

------

# 15. 核心对比

到这里可以把整章压缩成一张表：

| 特征         | Prefill         | Decode                  |
| ------------ | --------------- | ----------------------- |
| 一次处理     | 很多 token      | 每请求 1 个新 token     |
| 主要计算形态 | 大矩阵计算      | 较小矩阵/矩阵向量式计算 |
| 权重复用     | 高              | 单请求时低              |
| 简化算术强度 | $I\approx s$    | $I\approx B$            |
| 常见瓶颈     | Compute-bound   | Memory-bound            |
| 更关注       | 算力利用率      | 显存带宽                |
| 常见优化     | 高效 GEMM、并行 | Batch、量化、调度       |

最值得记住的不是这张表，而是：

```text
Prefill
很多 token
   ↓
同一份权重反复使用
   ↓
算术强度高
   ↓
更容易 Compute-bound


Decode
每请求每步只有 1 token
   ↓
仍需访问大量模型数据
   ↓
算术强度低
   ↓
更容易 Memory-bound
```

------

# 16. TPOT 下限

现在可以解释一个非常实际的问题：

> 一个 7B FP16 模型，生成一个 token 最快能有多快？

假设：

$P=7\times10^9$

FP16 每个参数：

$2\text{ Bytes}$

模型权重：

$7\times10^9 \times2$$= 14\times10^9 \text{ Bytes}$

也就是约：

$14\text{ GB}$

如果 Decode 处于 Memory-bound，并暂时忽略 KV Cache、通信、Kernel 等额外开销，那么理论搬运时间：

$\tau_{\min} = \frac{\text{权重字节数}} {\text{显存带宽}}$

代入：

$\tau_{\min} = \frac{ 14\times10^9 }{ 2.0\times10^{12} }$

计算：

$\tau_{\min} = 7\times10^{-3} \text{ s}$

因为：

$1\text{ s} = 1000\text{ ms}$

所以：

$\boxed{ \tau_{\min} \approx7\text{ ms} }$

### 符号说明

- $\tau$：希腊字母 tau，这里表示时间
- $\tau_{\min}$：理论最小时间
- TPOT：Time Per Output Token，每个输出 token 的平均生成时间

注意，这是**理想化带宽下界**。

真实系统还存在：

- KV Cache 访问
- 激活读写
- Kernel 开销
- GPU 未达到理论峰值带宽
- 多卡通信
- 调度开销

所以真实 TPOT 通常不会简单等于这个数字。

------

# 17. 量化为什么提速

现在把 FP16：

$2\text{ Bytes/parameter}$

变成 INT8：

$1\text{ Byte/parameter}$

7B 权重大小从约：

$14\text{ GB}$

下降为：

$7\text{ GB}$

重新计算理想搬运时间：

$\tau_{\min}^{INT8} = \frac{ 7\times10^9 }{ 2.0\times10^{12} }$

得到：

$\boxed{ \tau_{\min}^{INT8} \approx3.5\text{ ms} }$

所以在这个理想化、带宽主导的模型中：

```text
FP16
14 GB
 │
 ▼
7 ms


INT8
7 GB
 │
 ▼
3.5 ms
```

这揭示了量化的第二层价值。

很多人最初只知道：

> 量化 → 模型变小 → 省显存。

但在 Memory-bound Decode 中，还有：

> 量化 → 每一步需要搬的数据更少 → 理论带宽耗时降低。

所以量化可以同时影响：

```text
             权重量化
                │
        ┌───────┴───────┐
        ▼               ▼
     模型更小         搬运更少
        │               │
        ▼               ▼
    节省显存          Decode 更快
```

实际加速比例并不保证严格等于 2 倍，因为还取决于量化 Kernel、反量化开销、KV Cache、硬件支持等因素。

# 18. Roofline 总图

现在可以把整章放进一个统一框架：

```text
性能
 ▲
 │                         ─────────── 算力上限
 │                       /
 │                     /
 │                   /
 │                 /
 │               /
 │             ●
 │           I*
 │         /
 │       /
 │     /
 │   /
 └────────────────────────────────→ 算术强度 I

     Memory-bound       Compute-bound
        带宽限制            算力限制
```

左边：

$I$小于 $I^{*}$，程序数据复用不足。

提高纯计算峰值通常帮助有限，更应该减少数据搬运或提高复用。

右边：

$I>I^*$

数据已经足够喂饱 GPU。

这时候继续减少少量内存访问收益有限，更应该提升计算效率。

# 19. 优化地图

于是不同优化手段为什么有效，就可以从物理原因理解。

### Decode

```text
Decode
  │
  └─ Memory-bound
        │
        ├─ 增大 Batch
        │    └─ 提高权重复用
        │
        ├─ 权重量化
        │    └─ 减少搬运 Bytes
        │
        ├─ KV Cache 优化
        │    └─ 减少缓存流量/容量
        │
        └─ 算子与调度优化
             └─ 减少额外开销
```

### Prefill

```text
Prefill
  │
  └─ 通常算术强度较高
        │
        ├─ 高效 GEMM
        ├─ Tensor Core
        ├─ Tensor Parallel
        └─ 更高有效算力
```

这也是为什么 Prefill 和 Decode 虽然都在执行同一个 Transformer，却可能需要不同的资源优化策略。

# 20. 程序实例

可以用一个简单 Python 程序把本章几个公式计算出来：

```python
FLOPS_PEAK = 312e12
BW_PEAK = 2.0e12

P = 7e9


def machine_balance():
    return FLOPS_PEAK / BW_PEAK


def weight_size(P, bytes_per_param):
    return P * bytes_per_param


def ideal_decode_time(P, bytes_per_param):
    size = weight_size(P, bytes_per_param)
    return size / BW_PEAK


I_star = machine_balance()

fp16_time = ideal_decode_time(
    P,
    bytes_per_param=2
)

int8_time = ideal_decode_time(
    P,
    bytes_per_param=1
)

print(
    f"I* = {I_star:.0f} FLOP/byte"
)

print(
    f"FP16 ideal time = "
    f"{fp16_time * 1000:.2f} ms"
)

print(
    f"INT8 ideal time = "
    f"{int8_time * 1000:.2f} ms"
)
```

预期得到：

```text
I* = 156 FLOP/byte
FP16 ideal time = 7.00 ms
INT8 ideal time = 3.50 ms
```

# 21. 部署说明

实际部署时不要直接拿：

$I^*=156$

作为所有 GPU、所有模型的固定标准。

因为：

$I^* = \frac{\mathcal F} {\mathcal B}$

GPU 一换：

- 峰值算力变了
- 显存带宽变了
- 数据类型变了

机器平衡点自然也会改变。

实际系统还应该测量：

- 实际 HBM 带宽利用率
- Tensor Core 利用率
- SM 利用率
- Batch Size
- Prompt 长度
- KV Cache 大小
- TTFT
- TPOT

因此 Roofline 更适合回答：

> **我的优化方向应该首先瞄准哪里？**

而不是直接预测真实系统延迟。

# 22. 易错点

### 误区 1

> GPU 算力越高，LLM Decode 一定越快。

不一定。

如果 Decode 正处于 Memory-bound：

```text
计算单元本来就在等数据
```

继续增加计算峰值未必有明显收益。

------

### 误区 2

> 量化只是为了让模型装进显存。

不完整。

在 Memory-bound 阶段：

$\text{Bytes}\downarrow$

会直接降低：

$t_{\text{mem}} = \frac{\text{Bytes}} {\mathcal B}$

因此量化也可能直接改善 Decode 性能。

------

### 误区 3

> Batch 越大越好。

错误。

Batch 增大会提高数据复用，但同时：

- 显存占用增加
- KV Cache 增加
- 排队延迟可能增加
- 最终可能进入 Compute-bound

因此 Batch 是吞吐、显存和延迟之间的权衡。

------

### 误区 4

> Prefill 永远 Compute-bound，Decode 永远 Memory-bound。

这是很有用的工程概括，但不是数学定律。

准确说法应该是：

> **典型 LLM Serving 工作负载下，Prefill 通常具有较高算术强度，而 Decode 通常具有较低算术强度。**

最终仍然应该根据：

$I \quad\text{与}\quad I^*$

的关系判断。

# 23. 本章主线

这一章真正需要掌握的逻辑只有一条：

```text
GPU 做任务
   │
   ├──────────────┐
   ▼              ▼
搬数据           做计算
Bytes            FLOPs
   │              │
   └──────┬───────┘
          ▼
     算术强度 I
          │
          ▼
       与 I* 比
          │
     ┌────┴────┐
     ▼         ▼
   I<I*       I>I*
     │         │
     ▼         ▼
Memory-bound Compute-bound
```

然后把 LLM 放进去：

```text
                LLM Inference
                     │
            ┌────────┴────────┐
            ▼                 ▼
         Prefill            Decode
            │                 │
        多 token            单步 token
            │                 │
       权重复用高          权重复用低
            │                 │
        I ≈ s             I ≈ B
            │                 │
            ▼                 ▼
     常偏 Compute       常偏 Memory
```

理解这张图，本章基本就通了。

# 24. 直观理解

把 GPU 想成一家餐厅：**显存带宽是送食材的卡车，算力是厨师。** Decode 像每做一道菜都重新运一车食材，厨师经常等车；Prefill 像一次运来食材连续做几十道菜，厨师持续忙碌。Batch 是“一车食材同时服务更多客人”，量化则是“把食材包装压小，一辆车能运更多”。

# 25. 练习测评

先不要看任何答案，自己推。

## 第 1 题

某 GPU：

$\mathcal F = 200\text{ TFLOP/s}$

显存带宽：

$\mathcal B = 2\text{ TB/s}$

某程序算术强度：

$I=40\text{ FLOP/byte}$

回答：

1. 这张 GPU 的 $I^*$ 是多少？

   1. $I^* = \frac{\mathcal F}{\mathcal B} = \frac{200}{2} = 100\text{ FLOP/byte}$

2. 该程序更可能是 Memory-bound 还是 Compute-bound？

   1. $I<I^{*}$，更容易 Memory-bound

3. 如果只把 GPU 算力从 200 TFLOP/s 提高到 400 TFLOP/s，而显存带宽不变，你预计这个程序会不会获得接近 2 倍加速？为什么？

   1. 不会，当前程序的瓶颈主要在于搬运瓶颈，每搬运 1byte 仅能完成 40FLOP 运算，因此即使 GPU 算力翻倍也无济于事，必须先让搬运快起来。

   2. 原 GPU：

      $I^*_{\text{old}} = \frac{200}{2} = 100$

      算力翻倍：

      $I^*_{\text{new}} = \frac{400}{2} = 200$

      程序自身仍然：

      $I=40$

      于是：

      $40<200$

      仍然严重 Memory-bound。

      注意一个容易反直觉的地方：

      > **GPU 算力变强以后，机器平衡点反而从 100 上升到了 200。**

      因为“厨师”变得更快了，而“送菜速度”没变，所以厨师反而更容易等数据。

      因此优化方向应该是：

      **提高有效带宽 / 减少 Bytes / 提高数据复用率**，而不只是提高 FLOPS。

------

## 第 2 题

假设一个模型有：

$P=8\times10^9$

个参数。

采用 FP16，GPU 显存带宽：

$\mathcal B = 1.6\text{ TB/s}$

暂时忽略 KV Cache 和其他开销。

回答：

1. 模型权重约多少 GB？
   1.  $\text{权重大小}=\text{参数数量}\times\text{每参数字节数}$，则模型权重为 P * 16bit= 16GB
2. Decode 每一步仅搬一次完整权重，理论最低需要多少 ms？
   1. 模型权重/显存带宽 = 10ms
3. 如果换成 INT8，理论最低时间是多少？
   1. 模型权重减半，显存带宽不变，理论的 decode 单词搬运完整权重的时间也减半，为 5ms
4. 为什么这个计算可以帮助解释“量化能够加速 Decode”？
   1. 量化不仅仅减小了显存占用，更重要的是在 decode 中减少了搬运量。



## 最后一题

这题不需要复杂计算，专门检查你是否真正理解。

现在有两个 GPU：

|      | GPU A       | GPU B       |
| ---- | ----------- | ----------- |
| 算力 | 300 TFLOP/s | 600 TFLOP/s |
| 带宽 | 3 TB/s      | 3 TB/s      |

某 Decode 工作负载：

$I=50\text{ FLOP/byte}$

请回答三个问题：

1. GPU A 和 GPU B 的 $I^*$ 分别是多少？
2. 这个 Decode 在两张卡上分别属于什么瓶颈？
3. **GPU B 的算力是 A 的两倍，为什么实际 Decode 性能可能几乎没有两倍提升？**

第三问不要只回答“因为 Memory-bound”，试着从

$t_{\text{calc}} \quad\text{和}\quad t_{\text{mem}}$

谁更大的角度解释。

- 100FLOP/byte 和 200FLOP/byte；在两张卡上都是 Memory-bound瓶颈；因为 calc 时间在两个程序上都小于 mem 时间，搬运一次 mem 根本喂不饱嗷嗷待哺的 calc

GPU A：

$I_A^* = \frac{300}{3} = 100\text{ FLOP/byte}$

GPU B：

$I_B^* = \frac{600}{3} = 200\text{ FLOP/byte}$

程序本身：

$I=50\text{ FLOP/byte}$

因此：

$50<100<200$

所以在两张 GPU 上都是：

$\boxed{\text{Memory-bound}}$

更关键的是你第三问的解释。根据这一章采用的模型：

$t_{\text{step}} = \max ( t_{\text{calc}}, t_{\text{mem}} )$

GPU A 中：

$t_{\text{calc}} < t_{\text{mem}}$

升级到 GPU B 后，算力翻倍，于是：

$t_{\text{calc}}\downarrow$

但是显存带宽完全没变：

$\mathcal B_A = \mathcal B_B$

所以：

$t_{\text{mem}} = \frac{\text{Bytes}}{\mathcal B}$

基本没变。

最终依然：

$t_{\text{step}} \approx t_{\text{mem}}$

所以 GPU B 即使有 **2× 算力**，也不意味着这个 Decode 能获得 **2× 性能**。

你现在可以把这句话作为本章的核心直觉：

> **Memory-bound = 厨师不是做菜慢，而是在等食材。再雇一倍厨师没什么用；要么让卡车更快（提高带宽），要么每车装得更多（量化减少 Bytes），要么一车食材同时服务更多客人（增大 Batch、提高复用）。**

到这里，**“带宽与算力 → Arithmetic Intensity → Roofline → Prefill/Decode → Batch/量化”这条主线你已经掌握了。** 原笔记后面的部署决策，本质上就是把这套判断真正用于推理系统优化。
