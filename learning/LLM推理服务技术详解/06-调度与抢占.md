> 本章目标：理解推理引擎如何在多个请求之间分配 GPU 时间与 KV Cache，以及为什么 Continuous Batching、Chunked Prefill 和抢占会同时影响吞吐、TTFT 与 TPOT。

# 本章主线

```text
请求不断到达
    ↓
调度器选择本轮运行者
    ↓
检查算力预算与 KV Cache
    ↓
执行 Prefill / Decode
    ↓
完成者退出，新请求补位
    ↓
显存不足时触发抢占
```

上一章已经说明：Prefill 通常更偏向算力密集，Decode 通常更偏向带宽密集。二者若在同一轮执行，会争夺不同的硬件资源；调度器的任务，就是在吞吐、延迟和公平性之间做取舍。

# 前置基础

## 1. 自回归生成

Decode 每轮只能为每个序列生成一个新 token。下一轮必须依赖上一轮的结果，因此不能把一个请求的所有输出 token 一次算完。

## 2. KV Cache

已经处理过的 token 会留下 K、V 张量。后续 Decode 直接读取它们，避免重复计算；但上下文越长，KV Cache 占用越大。

## 3. 时间模型

在简化模型中：

\[
T_{\text{step}}
\overset{\text{取慢者}}{=}
\max\!\left(
T_{\text{calc}},
T_{\text{mem}}
\right)
\]

> 注：真实 GPU 上计算和访存不能总是完全重叠，所以这个式子用于判断主要瓶颈，不用于精确预测延迟。

# 模型与请求

| 名词               | 小白解释                 | 本章中的作用                 |
| ---------------- | -------------------- | ---------------------- |
| Model（模型）            | 由模型参数和计算结构组成的大模型     | 决定一次前向计算做哪些运算          |
| Inference（推理）        | 使用训练好的模型产生结果，不更新权重   | Prefill 和 Decode 都属于推理 |
| Serving（服务化）          | 将模型做成能同时响应许多用户的在线服务  | 排队、调度和抢占发生在这一层         |
| Inference Engine（推理引擎） | 执行模型并管理 GPU、显存和请求的软件 | 例如 vLLM、SGLang         |
| Request（请求）          | 用户提交的一次生成任务          | 一个请求包含许多 token         |
| Prompt（提示词）           | 用户已经提供的输入 token      | 首先进入 Prefill 阶段        |
| Sequence（序列）         | 请求当前的完整 token 序列     | 包含 Prompt 和已生成内容       |
| Context Length（上下文长度） | 当前序列已有的 token 数量     | 越长通常需要越多 KV Cache      |

可以把 **request、prompt、sequence** 看成大模型系统里三个不同层级的概念：

> **Sequence 是模型正在处理的 token 序列；Prompt 是你提供给模型的输入内容；Request 是一次完整的服务请求。**

## 三者定义

### 1. Prompt

**Prompt = 给模型的输入内容。**

例如你发送：

> 请用通俗语言解释什么是 CUDA。

这句话就是 prompt。

经过 tokenizer 后，它会变成：

$P= [t_1,t_2,\dots,t_n]$

**符号说明**

- $P$：Prompt 对应的 token 序列。
- $t_i$：第 $i$ 个 token。
- $n$：Prompt 长度。

在聊天模型里，Prompt 往往不只是你刚输入的那句话。

例如：

```
System Prompt
+
历史对话
+
用户最新问题
```

最终都会被整理成模型实际看到的输入。

所以：

> **Prompt 更关注“模型吃进去什么”。**

------

### 2. Sequence

**Sequence = 模型当前正在处理的一整条 token 序列。**

刚开始的时候：

$S_0=P$

**依据：生成尚未开始**

也就是 sequence 里暂时只有 prompt。

假设 Prompt 是：

```
法国的首都是
```

模型开始生成：

```
巴
```

那么：

$S_1= [P,\ t_{n+1}]$

**依据：追加第 1 个生成 token**

再生成：

```
黎
```

得到：

$S_2= [P,\ t_{n+1},t_{n+2}]$

**依据：继续追加生成 token**

所以可以写成：

$\text{Sequence} = \text{Prompt Tokens} + \text{Generated Tokens}$

也就是说：

> **Prompt 通常只是 Sequence 的前半部分。**

随着 Decode 不断进行，Prompt 不变，但 Sequence 会越来越长。

------

### 3. Request

**Request = 用户向推理服务提交的一次完整生成任务。**

例如调用一个 LLM API：

```
request = {
    "prompt": "法国的首都是",
    "max_tokens": 100,
    "temperature": 0.7
}
```

这里：

```
整个对象
        ↓
     Request
   ┌──────────────┐
   │ prompt       │
   │ max_tokens   │
   │ temperature  │
   │ stop         │
   │ ...          │
   └──────────────┘
```

所以：

> Prompt 是 Request 中的一部分。

Request 还可能携带：

```
request_id
model
prompt
max_tokens
temperature
top_p
stop
sampling parameters
...
```

因此 **Request 更偏推理服务/调度系统层面的概念**。

### 层级关系

把整个过程串起来：

```
用户
 │
 │ 发起
 ▼
┌────────────────────────┐
│        Request         │
│                        │
│ prompt                 │
│ max_tokens             │
│ temperature            │
│ sampling params        │
└───────────┬────────────┘
            │
            │ 取出 Prompt
            ▼
┌────────────────────────┐
│         Prompt         │
│                        │
│ "法国的首都是"          │
└───────────┬────────────┘
            │ Tokenizer
            ▼
       [t1 t2 ... tn]
            │
            │ 创建
            ▼
┌────────────────────────┐
│       Sequence         │
│                        │
│ t1 t2 ... tn           │ ← Prompt
└───────────┬────────────┘
            │
         Prefill
            ▼
       KV Cache 建立
            │
         Decode
            ▼
┌────────────────────────┐
│       Sequence         │
│                        │
│ t1 ... tn tn+1         │
│ t1 ... tn tn+1 tn+2    │
│ t1 ... tn ... tn+k     │
└────────────────────────┘
```

这里最重要的一点是：

$\boxed{ \text{Request} \supset \text{Prompt} }$

而从 token 内容角度：

$\boxed{ \text{Sequence} = \text{Prompt Tokens} + \text{Generated Tokens} }$

这两个关系不要混在一起。

### 批次与轮次

| 名词                  | 小白解释                   | 与相近概念的区别          |
| ------------------- | ---------------------- | ----------------- |
| Batch（批次）               | 某一轮一起送入 GPU 的一组序列      | 指“这一轮有哪些请求”       |
| Batch Size（批次大小）          | Batch 中的活跃序列数          | 不是上下文长度或 token 总数 |
| Iteration（迭代轮次）           | 调度器组装 batch 并执行一次模型的轮次 | 指“现在执行第几轮”        |
| Slot（槽位）                | 教学中表示 batch 内一个序列的位置   | 是逻辑位置，不是 GPU 真实插槽 |
| Static Batching（静态批处理）     | 组好一批后等待整批全部结束          | 短请求结束后会留下空槽位      |
| Continuous Batching（连续批处理） | 每轮结束后移除完成者并让新请求补位      | 又称迭代级调度或动态批处理     |

> Batch 是“这一轮有哪些序列”，Iteration 是“执行了第几轮”。Continuous Batching 下，每轮 Batch 的成员都可能变化。

### 生成阶段

| 名词           | 小白解释                     | 主要特点                    |
| ------------ | ------------------------ | ----------------------- |
| Prefill（预填充）      | 一次处理 Prompt 中已有的多个 token | 建立初始 KV Cache，通常计算密集    |
| Decode（解码）       | 根据已有上下文预测下一个 token       | 每条序列每轮通常生成一个 token      |
| Forward Pass（前向传播） | 输入穿过模型各层并得到输出的完整过程       | Prefill 和每轮 Decode 都会执行 |
| Logits（原始分数）       | 模型给词表中每个候选 token 的原始分数   | 还不是最终选中的 token          |
| Sampling（采样）     | 根据概率和解码规则选出下一个 Token ID  | 温度、Top-p 等在这里生效         |

### GPU 执行

#### Kernel

Kernel（GPU 内核）是一段在 GPU 上并行执行的小程序。这里的“内核”既不是操作系统内核，也不是整个大模型。

一次 Transformer 前向过程通常会启动许多 Kernel：

```text
矩阵乘 Kernel
    ↓
归一化 Kernel
    ↓
Attention Kernel
    ↓
激活函数 Kernel
```

CPU 发出启动指令后，GPU 上的大量线程共同执行该 Kernel。

| 名词              | 小白解释                  | 本章中的意义                     |
| --------------- | --------------------- | -------------------------- |
| Operator（算子）   | 从模型结构看的一项运算           | 一个算子可能由一个或多个 Kernel 实现     |
| Kernel（内核）          | 实际在 GPU 上执行某类并行运算的小程序 | 一轮模型计算会启动许多 Kernel         |
| Kernel Launch（内核启动）   | CPU 向 GPU 提交一次 Kernel | 每次启动都有固定软件开销               |
| Launch Overhead（启动开销） | 提交到开始执行之间的额外成本        | 小任务或小分块过多时更明显              |
| Kernel Fusion（内核融合）   | 将连续运算合并到更少的 Kernel    | 减少启动次数和中间数据搬运              |
| CUDA Graph（CUDA 图）      | 预先记录一串 GPU 操作并重复提交    | 减少 CPU 调度和 Launch Overhead |
| GPU Thread（GPU 线程）      | 执行 Kernel 的最小线程单位     | 大量线程共同完成矩阵运算               |
| SM（流式多处理器）              | GPU 中执行并调度线程块的计算单元    | SM 忙碌程度影响算力利用率             |

> 正确层级：模型由算子组成，算子最终由一个或多个 Kernel 在 GPU 上实现。

### 显存与传输

| 名词                | 小白解释                   | 容易混淆之处                 |
| ----------------- | ---------------------- | ---------------------- |
| VRAM / GPU Memory（显存） | GPU 可用的显存空间            | 表示“能装多少”，单位 GB         |
| HBM（高带宽内存）               | 数据中心 GPU 常见的高带宽显存      | 消费级 GPU 通常使用 GDDR      |
| Memory Capacity（显存容量）   | 显存总容量                  | 决定模型和 KV Cache 能否装下    |
| Memory Bandwidth（显存带宽）  | 每秒能从显存搬运多少数据           | 表示“搬多快”，单位 GB/s 或 TB/s |
| KV Cache（键值缓存）          | 各层为历史 token 保存的 K、V 张量 | 加速 Decode，但占用显存        |
| KV Block / Page（键值缓存块／页） | 管理 KV Cache 的固定大小逻辑块   | 便于分配、回收和共享             |
| PagedAttention（分页注意力）    | 按块管理非连续 KV Cache 的方法   | 类似操作系统的分页思想            |
| Fragmentation（碎片化）     | 空闲显存分散造成的空间浪费          | 分页式管理可减少外部碎片           |
| PCIe（高速串行计算机扩展总线）       | CPU 与 GPU 间常见的互连通道     | Swap 数据通常经过它或其他互连      |
| DMA（直接内存访问）              | 设备直接批量搬运数据的机制          | CPU 不必逐字节复制，但建立传输仍有开销  |
| Pinned Memory（锁页内存）     | 不会被操作系统换出的 CPU 内存      | 常用于更高效的 CPU–GPU 传输     |

> 显存容量是“仓库有多大”，显存带宽是“仓库门口每秒能搬多少货”，二者不能混为一谈。

### 调度与抢占

| 名词                    | 小白解释                    | 本章中的作用                      |
| --------------------- | ----------------------- | --------------------------- |
| Queue（队列）                 | 暂存尚未运行请求的等待队列           | GPU 忙或预算不足时先排队              |
| Scheduler（调度器）             | 决定下一轮运行哪些请求的软件模块        | 组装 Batch 并检查各种预算            |
| Token Budget（Token 预算）          | 一轮最多允许处理的 token 数       | 限制本轮总计算规模                   |
| KV Cache Budget（键值缓存预算）       | 本轮可分配的 KV Cache 空间      | 不足时不能无条件接纳请求                |
| Admission Control（准入控制）     | 请求进入执行系统前的准入控制          | 过载时排队、限流或拒绝                 |
| Backpressure（背压）          | 下游忙时通知上游降低发送速度          | 防止队列无限增长                    |
| FCFS（先到先服务）                  | 按到达顺序服务                 | 全称 First-Come, First-Served |
| Head-of-Line Blocking（队头阻塞） | 队首大任务挡住后面的短任务           | 长 Prefill 阻塞 Decode 就是例子    |
| Preemption（抢占）            | 暂停未完成请求并收回其资源           | 后续需要恢复                      |
| Recompute（重新计算）             | 丢弃 KV Cache，恢复时重新计算     | 用 GPU 算力换显存空间               |
| Swap-out（换出）              | 将 KV Cache 从 GPU 搬到 CPU | 消耗互连带宽和 CPU 内存              |
| Swap-in（换入）               | 将 KV Cache 从 CPU 搬回 GPU | 恢复时再次传输                     |
| Aging（老化）                 | 等待越久，调度优先级逐渐提高          | 防止低优先级请求饿死                  |
| Starvation（饥饿）            | 某请求长期得不到执行机会            | 调度不公平可能导致它                  |

### 性能指标

| 名词          | 小白解释                | 如何观察                 |
| ----------- | ------------------- | -------------------- |
| Throughput（吞吐量）  | 整个系统单位时间完成的工作量      | token/s 或 request/s  |
| Latency（延迟）     | 一个请求等待或执行了多久        | ms 或 s               |
| TTFT（首 Token 延迟）        | 请求到达至首 token 返回的时间  | “多久开始回答”             |
| TPOT（平均每输出 Token 耗时）        | 输出阶段平均每个新 token 的耗时 | “平均输出多快”             |
| ITL（Token 间延迟）         | 两个相邻输出 token 的实际间隔  | “中途是否卡顿”             |
| P50（第 50 百分位数）         | 50% 样本不超过该值         | 表示典型情况               |
| P95 / P99（第 95／99 百分位数）   | 95% / 99% 样本不超过该值   | 观察少数慢请求的尾延迟          |
| Utilization（利用率） | 某种资源被使用的比例          | 必须说明是槽位、SM、带宽还是显存    |
| SLO（服务级别目标）         | 服务承诺达到的性能目标         | 如 99% 请求 TTFT 小于 1 秒 |

> 吞吐回答“系统总共做了多少”，延迟回答“某个用户等了多久”。吞吐提高不保证每个请求都更快。

## 调度对象

先分清三个层次：

| 层次      | 决定什么                              | 例子                  |
| ------- | --------------------------------- | ------------------- |
| 请求级     | 哪个请求先进入系统                         | FCFS、优先级队列          |
| 迭代级     | 下一轮让哪些序列运行                        | Continuous Batching |
| Token 级 | 本轮给 Prefill 和 Decode 各多少 token 预算 | Chunked Prefill     |

“调度”不只是给请求排队。LLM Serving 的关键变化，是调度器可以在每一次模型迭代前重新组装 batch。

## 静态批处理

设一个静态 batch 中有 $B$ 个请求。第 $i$ 个请求需要生成 $N_i$ 个 token，每次 Decode 迭代耗时近似为 $\tau$。

由于整批必须等待最长请求完成：


$$
T_{\text{batch}}
\overset{\text{最长请求}}{=}
\tau
\max_i N_i
$$


所有请求真正完成的有效槽位工作量是：

$$
W_{\text{useful}}
\overset{\text{逐项相加}}{=}
\tau
\sum_{i=1}^{B}N_i
$$

整个 batch 占用的槽位容量是：


$$
W_{\text{capacity}}
\overset{B\text{ 个槽位}}{=}
B\tau
\max_i N_i
$$


因此槽位利用率：


$$
U
\overset{\text{利用率定义}}{=}
\frac{W_{\text{useful}}}
{W_{\text{capacity}}}
$$


代入上面两式：


$$
U
\overset{\text{代入}}{=}
\frac{
\tau\sum_{i=1}^{B}N_i
}{
B\tau\max_iN_i
}
$$


约去 $\tau$：


$$
U
\overset{\text{约去 }\tau}{=}
\frac{
\sum_{i=1}^{B}N_i
}{
B\max_iN_i
}
$$


### 数值例子

9 个请求各输出 10 token，1 个请求输出 1000 token：

\[
\sum_iN_i
\overset{\text{求和}}{=}
9\times10+1000
\]

\[
\sum_iN_i
\overset{\text{计算}}{=}
1090
\]

\[
U
\overset{\text{代入}}{=}
\frac{1090}{10\times1000}
\]

\[
U
\overset{\text{除法}}{=}
10.9\%
\]

短请求完成后，它们对应的槽位持续空闲，却不能接收新请求。这就是静态 batching 的“木桶效应”。

> 这里的 \(U\) 是教学用的槽位利用率，不等同于监控工具里的 GPU Utilization 或 SM Active。

## 连续批处理

Continuous Batching 也叫迭代级调度。这里的“迭代”是调度器组装一个 Batch 并完成一次模型执行的轮次。它不等整批请求全部结束，而是在每轮 Decode 后重新检查：

1. 哪些请求已经结束；
2. 哪些请求仍需继续 Decode；
3. 等待队列中哪些请求可以补位；
4. 本轮 token 与 KV Cache 预算是否足够。

### 运行示例

<img src="https://fakercodes.oss-cn-hangzhou.aliyuncs.com/sl/ChatGPT%20Image%202026%E5%B9%B49%E6%9C%8815%E6%97%A5%2021_04_13.png" alt="ChatGPT Image 2026年9月15日 21_04_13" style="zoom: 33%;" />

它的优势不是“让每个请求单独跑得更快”，而是减少空槽位，使同一次权重读取服务更多请求，从而提升总体吞吐。

### 必须修正

连续批处理会提高利用率，但不能写成 \(U\to1\) 的必然结论。以下因素仍会留下空洞或开销：

- 请求到达率不足，没有新请求补位；
- KV Cache 不够，等待请求无法进入；
- 序列长度不同导致 Kernel 的输入形状不规整；
- 调度、采样和 Kernel Launch（CPU 提交 GPU 小程序）有固定成本；
- 批次过大后，单轮时间上升并损害延迟。

## 三类延迟

| 指标   | 起点 → 终点           | 用户感受      |
| ---- | ----------------- | --------- |
| TTFT | 请求到达 → 首 token 返回 | “多久开始回答”  |
| TPOT | 相邻输出 token 的平均间隔  | “平均输出有多快” |
| ITL  | 某两个相邻 token 的实际间隔 | “输出是否卡顿”  |

吞吐与延迟不是同一个目标。增大 batch 往往能提高系统总吞吐，但也可能增加排队时间和单轮执行时间。

### 一个常见冲突

- Prefill 优先：新请求更快得到首 token，TTFT 较好；已有 Decode 可能被阻塞，ITL 出现尖刺。
- Decode 优先：已有用户的输出更平稳；新请求等待更久，TTFT 变差。

因此调度策略本质上是在分配“谁承担等待”。

---

## 队首阻塞

假设正在稳定 Decode，突然到达一个 8000-token Prompt。如果整段 Prefill 一次执行，它会形成一个很大的计算任务。Decode 请求必须等待这轮结束，因而 ITL/TPOT 出现尖刺。

原笔记用

\[
\frac{2P(s_p+B)}{\mathcal F}
\]

估计混合轮次的计算时间。这个式子可以表达“工作量随 Prefill token 数增加”，但必须注明它是近似上界式思考，不能直接当作实测延迟，原因包括：

- Attention 的计算量还随序列长度变化；
- Prefill 与 Decode 的 Kernel 形态不同；
- 实际算力低于硬件峰值且随形状改变；
- 两类任务的访存、通信和调度开销没有写入。

可靠的工程方法是测量不同 Prefill 块大小下的 TTFT、ITL 和吞吐，而不是只用峰值 FLOPS 推断。

---

## 分块预填充

Chunked Prefill 把长 Prompt 切成多个较小块，让 Decode 请求可以穿插在块与块之间运行。

设 Prompt 长度为 \(s_p\)，每块最多 \(c\) 个 token，则块数为：

\[
K
\overset{\text{向上取整}}{=}
\left\lceil
\frac{s_p}{c}
\right\rceil
\]

若：

\[
s_p=8000,
\qquad
c=512
\]

则：

\[
K
\overset{\text{代入}}{=}
\left\lceil
\frac{8000}{512}
\right\rceil
\]

\[
K
\overset{\text{计算}}{=}
16
\]

最后一块包含 token 数量：

\[
r
\overset{\text{减去前 15 块}}{=}
8000-15\times512
\]

\[
r
\overset{\text{计算}}{=}
320
\]

### 大块与小块

| 块大小 | 好处                      | 代价                               |
| --- | ----------------------- | -------------------------------- |
| 较大  | Prefill 更连续，矩阵更大，吞吐通常更好 | Decode 等待更久，尾延迟更差                |
| 较小  | 更容易穿插 Decode，ITL 更平稳    | 调度与 Kernel 启动开销增加，Prefill 效率可能下降 |

所以 \(c\) 不是越小越好。它是 TTFT、ITL 与吞吐之间的旋钮。

---

## 显存不足

调度器每轮不仅检查计算预算，还要为新 token 分配 KV Cache 空间。若可用 KV 块不足，通常有四类动作：

1. **等待**：不接纳新请求，让正在运行的请求先释放空间；
2. **抢占**：暂停部分请求，将资源让给其他请求；
3. **拒绝或限流**：在入口控制负载；
4. **扩容或降内存**：增加实例、降低并发、量化 KV Cache 等。

抢占不是免费扩容。它只改变资源使用顺序，并引入恢复成本。

---

## 抢占状态

一个请求可抽象为：

```text
Waiting → Running → Finished
              ↓
          Preempted
              ↓
        Waiting / Running
```

被抢占后，模型权重仍在 GPU；需要处理的是该请求的 KV Cache 与调度状态。

### 方式一：重算

Recompute 丢弃该请求的 KV Cache。请求恢复时，从已有 token 重新执行 Prefill，重建 KV Cache。

优点：不需要 CPU 侧保存大量 KV 数据。

缺点：重复消耗 GPU 算力，并增加恢复延迟。

### 方式二：换出

Swap-out 把 KV Cache 从 GPU 搬到 CPU 内存；恢复时再 Swap-in。数据通常经过 PCIe 等互连，并由 DMA 机制负责大块传输。

优点：避免重算已经完成的模型前向过程。

缺点：占用 CPU 内存与互连带宽，还涉及 DMA、页锁定内存和块表管理。

---

## 理想模型

设上下文长度为 \(n\)，每 token 的 KV Cache 为 \(S_{kv}\)。完整换出再换入共传输两次：

\[
T_{swap}
\overset{\text{时间公式}}{=}
\frac{2S_{kv}n}
{\mathcal B_{io}}
\]

若重算吞吐近似恒定为 \(R_{pre}\)：

\[
T_{re}
\overset{\text{时间公式}}{=}
\frac{n}{R_{pre}}
\]

比较两种时间：

\[
\frac{T_{swap}}{T_{re}}
\overset{\text{代入}}{=}
\frac{
2S_{kv}n/\mathcal B_{io}
}{
n/R_{pre}
}
\]

约去 \(n\)：

\[
\frac{T_{swap}}{T_{re}}
\overset{\text{约去 }n}{=}
\frac{
2S_{kv}R_{pre}
}{
\mathcal B_{io}
}
\]

因此在这个理想模型里，Swap 更快的条件是：

\[
T_{swap}<T_{re}
\]

\[
\overset{\text{代入并移项}}{\Longrightarrow}
\mathcal B_{io}

>

2S_{kv}R_{pre}
\]

这说明互连越快、KV 越小、Prefill 越快，选择会发生变化。

### 结论边界

“选择与 \(n\) 无关”只在下面四个条件同时成立时有效：

1. 没有固定开销；
2. Prefill 吞吐不随长度变化；
3. 传输带宽不随数据量与并发变化；
4. 换出和换入都必须完整发生，且不能与其他工作重叠。

真实系统通常不满足全部条件，所以不能只看 PCIe 标称带宽决定策略。

---

## 修正模型

加入固定开销：

\[
T_{swap}
\overset{\text{加入固定项}}{=}
C_{swap}
+
\frac{2S_{kv}n}
{\mathcal B_{io}}
\]

\[
T_{re}
\overset{\text{加入固定项}}{=}
C_{re}
+
\frac{n}{R_{pre}}
\]

令二者相等，求策略切换的上下文长度：

\[
C_{swap}
+
\frac{2S_{kv}n}{\mathcal B_{io}}
\overset{\text{临界条件}}{=}
C_{re}
+
\frac{n}{R_{pre}}
\]

移走固定项：

\[
C_{swap}-C_{re}
\overset{\text{移项}}{=}
n\left(
\frac{1}{R_{pre}}
-
\frac{2S_{kv}}{\mathcal B_{io}}
\right)
\]

解出 \(n\)：

\[
n^*
\overset{\text{两边同除}}{=}
\frac{
C_{swap}-C_{re}
}{
\frac{1}{R_{pre}}
-
\frac{2S_{kv}}{\mathcal B_{io}}
}
\]

其中 \(n^*\) 只有在分母为正且结果为正时，才表示有效的切换点。若分母不为正，Swap 的单位 token 成本不占优势，增加序列长度也不会让它反超。

## 调度策略

### FCFS

First-Come, First-Served 按到达顺序服务，简单且容易理解，但长 Prompt 可能阻塞后续短请求。

### 短任务优先

若能估计剩余长度，可优先短任务，降低平均完成时间。但用户通常不提前声明准确输出长度，而且长任务可能饥饿。

### Decode 优先

优先保护已开始生成的请求，使 ITL 更稳定；代价是等待中的 Prefill 请求 TTFT 增加。

### 优先级调度

为不同请求或租户配置优先级。必须配合 aging、配额或等待上限，否则低优先级请求可能长期得不到服务。

### 公平调度

公平不等于每轮给每个请求相同 token。长上下文请求每生成一个 token 会读取更多 KV Cache，因此“相同 token 数”并不代表“相同资源成本”。生产系统更适合按 GPU 时间、token 成本或 SLO 达成率衡量租户公平性。

---

## 公平指数

设 \(m\) 个租户获得的有效吞吐分别为 \(x_1,\ldots,x_m\)，Jain 公平性指数为：

\[
J
\overset{\text{定义}}{=}
\frac{
\left(\sum_{i=1}^{m}x_i\right)^2
}{
m\sum_{i=1}^{m}x_i^2
}
\]

完全公平时，令每个租户都得到 \(x\)：

\[
J
\overset{x_i=x}{=}
\frac{(mx)^2}{m(mx^2)}
\]

\[
J
\overset{\text{展开并约分}}{=}
1
\]

若只有一个租户获得全部资源：

\[
J
\overset{\text{仅一个非零}}{=}
\frac{x^2}{mx^2}
\]

\[
J
\overset{\text{约去 }x^2}{=}
\frac1m
\]

因此：

\[
\frac1m
\le J\le
1
\]

但 \(J\) 只描述分配是否均匀，不能代替 SLO。所有租户都很慢时，\(J\) 仍可能等于 1。

## 程序实例

下面的程序比较 Swap 与 Recompute，并显示固定开销如何产生长度相关的策略切换。

```python
KV_BYTES_PER_TOKEN = 524_288
PREFILL_TOKENS_PER_S = 20_000


def compare_preemption(
    context_tokens,
    io_gb_per_s,
    swap_fixed_ms=1.0,
    recompute_fixed_ms=0.2,
):
    io_bytes_per_s = io_gb_per_s * 1e9

    swap_ms = (
        swap_fixed_ms
        + 2
        * KV_BYTES_PER_TOKEN
        * context_tokens
        / io_bytes_per_s
        * 1000
    )

    recompute_ms = (
        recompute_fixed_ms
        + context_tokens
        / PREFILL_TOKENS_PER_S
        * 1000
    )

    choice = (
        "swap"
        if swap_ms < recompute_ms
        else "recompute"
    )

    return swap_ms, recompute_ms, choice


for tokens in (200, 1000, 4000):
    result = compare_preemption(
        context_tokens=tokens,
        io_gb_per_s=25,
    )
    print(tokens, result)
```

### 运行方法

1. 保存为 `preemption_demo.py`；
2. 在终端执行 `python3 preemption_demo.py`；
3. 修改 `io_gb_per_s`、固定开销和上下文长度；
4. 观察推荐策略是否发生变化。

这些常量只是教学样例。部署时应换成当前模型、当前硬件和当前负载下的实测值。

---

## 部署方法

不要一上来寻找“最佳 batch”。按下面顺序测量：

1. 固定模型、精度、GPU 数和请求长度分布；
2. 从低并发逐步增加请求率；
3. 同时记录吞吐、TTFT、TPOT/ITL 的 P50、P95、P99；
4. 记录 KV Cache 使用率、等待队列长度和抢占次数；
5. 若长 Prompt 导致 ITL 尖刺，再测试不同 Prefill 块大小；
6. 若持续抢占，优先检查容量与准入控制，而不是把抢占当成常态。

### 现象诊断

| 现象            | 更可能的原因              | 优先动作                  |
| ------------- | ------------------- | --------------------- |
| 吞吐低、GPU 也不忙   | 到达率低或 batch 太小      | 增加并发并检查请求队列           |
| 吞吐升高、TTFT 恶化  | 排队或 batch 过大        | 设置 token 预算与准入限制      |
| ITL 偶发巨大尖刺    | 长 Prefill 阻塞 Decode | 启用并调节 Chunked Prefill |
| 抢占持续出现        | KV Cache 容量不足       | 降并发、缩短上下文、扩容          |
| 个别租户长期超时      | 优先级或配额失衡            | 加 aging、租户配额与限流       |
| 平均延迟正常、P99 很差 | 队首阻塞或负载突发           | 看尾延迟与请求长度分布           |

> 软件参数名和默认值会随版本变化。配置 vLLM 或 SGLang 时，应先查当前版本文档，再以压测结果确定数值，不要照抄固定的 512、0.85 或 5% 阈值。

## 易错点

### 误区 1

“Continuous Batching 会降低每个请求的计算量。”

不会。它主要减少空槽位、提高权重和硬件的利用率。

### 误区 2

“Batch 越大，服务一定越好。”

Batch 增大通常有利于吞吐，却可能增加排队时间、单轮耗时和 KV Cache 压力。

### 误区 3

“抢占能解决显存不足。”

抢占只能暂时腾出空间，而且恢复要付出换入或重算成本。持续抢占通常意味着系统过载或容量配置不合理。

### 误区 4

“Swap 一定比 Recompute 快，因为不用重复计算。”

若 CPU–GPU 互连慢、固定开销高，或者 CPU 内存压力大，Swap 可能更慢。

### 误区 5

“平均 TPOT 正常，用户体验就正常。”

平均值会掩盖偶发停顿。交互式服务必须同时观察 ITL 的 P95/P99。

---

## 本章总结

1. 静态 batching 的问题是短请求结束后留下空槽位；
2. Continuous Batching 在迭代边界补位，提高整体吞吐；
3. 长 Prefill 会阻塞 Decode，造成 ITL 尾延迟尖刺；
4. Chunked Prefill 用更多轮次换取更平稳的 Decode；
5. KV Cache 不足时可等待、限流或抢占；
6. Recompute 用算力换空间，Swap 用互连与 CPU 内存换空间；
7. 调度没有单一最优解，必须围绕吞吐、TTFT、ITL、显存和公平性联合压测。

## 直观理解

把 GPU 看成只有一口灶的餐厅：Continuous Batching 是空座立刻补客；长 Prefill 像一道耗时大菜，会让其他桌断餐；Chunked Prefill 是把大菜拆成小盘穿插制作；抢占则是暂存半成品或稍后重做。调度器决定谁先吃、谁等待，以及餐厅是否过载。
