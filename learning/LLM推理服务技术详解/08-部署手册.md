# 八、部署手册

## 8.1 调参顺序（按影响力排序）

1. **确定模型与精度** —— 直接决定权重显存与 TPOT 下限（§五）
2. **测出你的瓶颈区** —— 逐步提高 batch，看吞吐是否还涨（§五 部署说明）
3. **设 `--max-model-len`** —— 防止单条请求吃光 KV
4. **设 `--gpu-memory-utilization`** —— 0.85~0.90，留激活峰值余量
5. **开 `--enable-chunked-prefill`** —— 治 TPOT 尖刺
6. **开 `--enable-prefix-caching`** —— 共享 System Prompt 场景收益巨大
7. **调 `--max-num-seqs`** —— 并发硬闸门，配合 SLO 反推
8. **上 KV 量化 / 权重量化** —— 前面都做完仍不够时的放大器

## 8.2 由 SLO 反推并发上限

$$
\begin{aligned}
N_{\text{conc}} &\leq \frac{M_{\text{kv}}}{S_{kv} \cdot \bar{s}} && \text{（显存硬约束：总 KV ÷ 单条占用）}\\
\tau(B) &\leq \tau_{\text{SLO}} && \text{（延迟硬约束：单步耗时不超 SLO）}\\
N_{\text{conc}} &= \min\left(\frac{M_{\text{kv}}}{S_{kv}\bar{s}},\ B_{\max}\right) && \text{（两个约束取交集，取较小者）}
\end{aligned}
$$

**注意这里的取舍**：单纯增大并发会让 KV 读取量 $B S_{kv} s$ 增长，$\tau$ 随之上升（§五 推导二的分母项）。所以**并发不是越大越好**，存在使吞吐最大、且 $\tau$ 仍达标的最优点。

## 8.3 完整启动示例

```bash
python -m vllm.entrypoints.openai.api_server \
    --model meta-llama/Llama-3-8B-Instruct \
    --tensor-parallel-size 2 \
    --max-model-len 8192 \
    --gpu-memory-utilization 0.88 \
    --max-num-seqs 256 \
    --max-num-batched-tokens 2048 \
    --enable-chunked-prefill \
    --enable-prefix-caching \
    --kv-cache-dtype fp8_e5m2 \
    --swap-space 32
```

**逐项说明**：

| 参数 | 作用 | 对应章节 |
|---|---|---|
| `--tensor-parallel-size 2` | TP 并行，切矩阵降单步延迟 | 五、七 |
| `--max-model-len 8192` | 限制单请求长度，防止 KV 被单条吃光 | 三 |
| `--gpu-memory-utilization 0.88` | 水位，留 12% 给激活峰值 | 三、四 |
| `--max-num-seqs 256` | 并发硬闸门（准入控制） | 六 |
| `--max-num-batched-tokens 2048` | Chunked Prefill 的块上限，治尖刺 | 六 |
| `--enable-prefix-caching` | 共享前缀 KV 复用 | 七 |
| `--kv-cache-dtype fp8_e5m2` | KV 量化，并发近乎翻倍 | 三 |
| `--swap-space 32` | 32 GB CPU 内存用于抢占时换出 | 六 |

## 8.4 排障速查

| 现象 | 最可能原因 | 排查点 |
|---|---|---|
| TTFT 突然飙升 | 排队变长 | 看队列长度与 `--max-num-seqs` 是否打满 |
| TPOT 偶发巨幅尖刺 | 长 prefill 干扰 或 抢占 | 看是否有超长请求；看抢占计数 |
| 抢占率 > 5% | 容量不足 | 扩容或收紧 `--max-num-seqs` |
| 显存随长上下文加速上涨 | 注意力矩阵被实体化 | 检查是否真用了 Flash 内核 |
| 平均 TPOT 达标但用户喊卡 | 只看均值 | 改看 **P99 ITL** |
| 加 batch 吞吐不涨 | 已进算力瓶颈区 | 停止加 batch，改降精度或换策略 |
